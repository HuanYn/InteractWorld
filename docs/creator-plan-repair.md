# 有界计划自修复：输入检查反馈闭环

本轮只增强 Creator 的动作规划 Agent：模型提出计划，程序反馈具体错误，模型最多修订一次，再由服务端独立检查。视频基座、训练权重和视频生成方式不变。这里的“修复”是修复**控制输入计划**，不代表视频画质改善或画面已执行目标。

## 与已有功能的区别

| 功能 | 处理对象 | 是否生成新视频 |
|---|---|---|
| 本轮计划自修复 | 本次模型提案中的格式、遗漏动作、时间与保护范围错误 | 不会自动生成；最多两轮提案形成一个最终版本 |
| 人工多轮编辑 | 用户对已保存计划提出的新要求 | 创建新版本，仍需明确确认生成 |
| 视觉反馈修订 | 从已生成视频观察到的问题 | 默认关闭，未因本轮修改开启 |
| 失败视频重试 | 已通过输入检查、但生成任务执行失败的同一计划 | 用户显式重试，不重新调用规划模型 |

它是一个受限的“提案—检查—修订”工作流，不是任意语义的自主 Agent，也不是自动玩游戏或导航系统。

## 单次请求的处理流程

1. **锁定请求与历史基线。** `POST /api/plan` 继续接收原始 `text`、`request_id` 和可选的 `session_id`、`base_version_id`。场景和 seed 沿用既有会话约束。历史基线由应用选择，不由模型在修订时更换。
2. **程序前置检查。** `diagnose_proposal(text, previous)` 检查请求是否落在当前受支持的控制语法内。无效基线、歧义、非法时间或不支持的操作直接停止，不加载模型来猜测答案。
3. **模型首次提案。** 合格请求进入本地模型。既支持原有完整 `action_segments`，也支持按键时间轨的 `replace_intervals` Patch。模型必须返回完整的约定结构。
4. **独立检查提案。** 检查结构、合法按键、时长、用户要求的动作与顺序，以及逐帧保留约束。模型自报“ready”或“已保留”不是执行许可。
5. **最多修订一次。** 只有可修复的模型错误才返回给模型。修订上下文包含原始请求、原历史基线、被拒绝的提案和结构化反馈；不提供一份程序算好的完整正确答案。要求模型返回完整的新提案，而不只是补一个遗漏字段。
6. **停止并再次复验。** 第二次仍失败就停止，没有第三轮。模型明确请求澄清或表示不支持也停止，不自动将拒绝改成可执行。服务收到最终提案后再次调用 `plan_request()`，只有通过该检查的计划可供用户提交生成。

例如，“前4秒向右移动，然后低头2秒”的提案若遗漏低头，检查器可返回 `missing_actions` 和 `missing_keys: ["K"]`。模型必须重新核对原话、补全两段动作并保持正确时间。这个例子说明机制，**不是对当前模型必能修好的承诺**。

## 错误分类与停止条件

`training/creator/planner.py` 的 `diagnose_proposal()` 返回 `plan` 和 `feedback`。`feedback` 采用稳定错误码、布尔值 `repairable`、简短 `message`，必要时带有限的 `missing_keys`、`extra_keys` 或 `protected_keys`。

| 类型 | 错误码 | 行为 |
|---|---|---|
| 请求或基线问题 | `invalid_baseline`、`request_ambiguous`、`request_unsupported` | 前置停止，不猜测用户要求 |
| 模型主动拒绝／澄清 | `model_declined` | 停止，不强制变为 ready |
| 非法输出格式 | `invalid_model_json`、`invalid_structure` | 原请求合法时最多重提一次 |
| 动作遗漏或增加 | `missing_actions`、`unexpected_actions` | 指出涉及按键，最多修订一次 |
| 时间或时长错误 | `timing_mismatch`、`duration_mismatch` | 要求重新核对原始时间描述，最多修订一次 |
| 修改范围越界 | `scope_mismatch`、`protected_track_changed` | 指出范围或受保护按键，最多修订一次 |
| 输入通过 | `accepted` | 结束提案，不继续调用模型 |

JSON 错误不会通过字符串补括号、抽取片段等手段静默“修好”。原始输出保留，由模型在同一请求内重新输出合法提案。新的提案仍接受完整检查。

模型执行异常、资源不足或超时属于运行失败，不等于计划修订成功，不会生成伪造的最终 ready 结果。GPU 授权、空闲卡检查、共享租约和有限作业时长继续由已有外部门禁负责。

## 同一请求只加载一次模型

`training/creator/model_worker.py` 中的 `_ModelSession` 按请求创建、延迟加载：

- 前置拒绝：`model_load_count = 0`，`attempts = []`。
- 进入模型提案：加载一次模型与 processor；如需第二轮，复用同一对象、同一进程和原有任务边界。
- 每次请求最多两次文本生成；没有为了修订再启动一个模型加载进程。
- 请求结束后 worker 退出，不把模型变成常驻 GPU 服务；下一次独立请求仍可能重新加载。

这避免了**同一请求第二轮修订**重复导入与加载，不保证消除首次冷启动开销，也不等于跨请求缓存。视频生成与语言／视觉模型继续遵守部署的串行资源门禁。

轨迹中的 `elapsed_seconds` 是该轮工作器耗时：首次轮次包含延迟加载和检查，修订轮次复用模型。不能把它不加区分地写成纯模型推理速度，也不能仅由模型加载次数推导实际节省时间。

## 接口、最终版本与页面记录

外部 API 不接受用户提交的 `planning_trace` 来授权动作。真实 worker 在最终 proposal 外附加轨迹；`CommandProvider.plan_with_trace(text, previous)` 将响应拆成：

```json
{
  "proposal": {"...": "最终模型提案字段"},
  "planning_trace": {"...": "工作器产生的有界检查记录"}
}
```

上述是接口结构示意，不是可执行请求或实测记录。原 `CommandProvider.plan()` 仍只返回 proposal，兼容旧的调用方。不支持新接口的旧 provider 继续按原路径执行，不伪造修订记录。

轨迹 `schema_version = 1`，保存：

- `max_revisions = 1`、`revision_count` 为 0 或 1。
- `model_load_count` 为 0 或 1。
- `outcome`：`first_pass`、`repaired`、`failed`、`needs_clarification` 或 `unsupported`。
- `attempts`：最多两条，含轮次、输入检查状态、结构化反馈和本轮耗时。

服务限制轨迹字段、长度、合法按键和数值范围。异常轨迹不被信任，会标注 `planning_trace_unavailable`；它无权覆盖 `plan_request()` 的最终状态。两轮模型提案只保存**一个最终版本**，而不是把被拒绝的第一稿也当作可生成版本。重复的 `request_id` 继续幂等复用原结果，不重新跑修订循环。

页面在本次计划区和版本卡显示“初次检查 → 一次修订检查 → 服务端最终计划”，并提供计划 JSON 导出。动态文字使用 `textContent`，不执行模型反馈中的 HTML。修订失败显示为“模型规划未通过”，不把模型漏项说成用户指令有歧义。旧版本没有轨迹时不补写虚构记录。

最终为 ready 仍需用户点击“确认并生成”。本次更新没有增加自动视频提交、自动接受版本或自动视觉修订。

## 能力边界与结果解读

该闭环依赖当前有限的中文动作／时间解析器：W/A/S/D 移动和 I/J/K/L 镜头控制、15秒／240个控制帧、16 FPS 时间边界，以及已有的局部时长编辑与历史版本保护语义。模型不能通过“修复”绕过不支持的输入。

- “到桥边再回头看山”包含目标识别、到达判定和空间导航，不能假装等价于按几秒 W 和 J。
- 保留的是未修改控制轨，不是重新生成视频中完全不变的像素。
- 输入检查通过不证明动作在画面中正确、及时地发生，更不证明人物稳定或视频更好看。
- 修订失败属于有效负结果；明确选择规则模式可以处理已知语法，但必须标注来源，不能算成模型自修复成功。
- CPU／浏览器测试验证的是边界、状态和展示，不是模型理解准确率。实际修订收益与延迟需单独按固定真实请求统计，不从功能上线推断。

相关实现：`training/creator/planner.py`、`training/creator/model_worker.py`、`training/creator/providers.py`、`training/creator/service.py`、`training/creator/page.py`。历史基线与秒数编译细节见 [精确时间线编辑与历史版本分支](creator-timeline-edit.md)。

## 2026-09-26：固定小样本实机结果

代码版本`3542ab163fed5cb75294e4300f599b70d8efd21a`，使用已有本地Qwen3-VL-4B-Instruct与3090 GPU2，没有新增训练。273项相关CPU检查、14项无头Edge浏览器行为检查通过；后者的接口是测试替身，不是真实模型证据。

首个真实请求在权重加载阶段达到480秒守卫限时，没有生成提案；失败及约0.142 GPU小时计费保留。随后仅做一次有界CPU顺序读取已有8.876GB权重，56.810秒完成，再以相同代码、相同固定请求复验。未改提示词、未下载或复制权重；以下客户端时间不包含该准备和之前的失败。

| 固定请求 | 首次结果 | 一次修订后／最终结果 | 本次客户端耗时 |
|---|---|---|---|
| 前4秒向右移动，然后低头2秒 | 正确 | D `[0,4)`，K `[4,6)`，未修订 | 23.606秒 |
| 前3秒向左移动，然后抬头2秒 | 非法JSON | 模型重新输出后正确：A `[0,3)`，I `[3,5)` | 17.235秒 |
| 保持前进不变，只在第8到10秒抬头，其他不要动 | 正确 | 指定历史基线，W240帧保持、I32帧，未修订 | 14.121秒 |
| 第0.1到1秒抬头 | 前置时间检查拒绝 | 0次模型加载，要求澄清 | 0.971秒 |
| 走到桥边 | 前置能力检查拒绝 | 0次模型加载，不支持精确导航 | 0.972秒 |

前3条可执行请求由首次正确2/3变为最多一次修订后3/3；后2条拒绝案例不计入模型正确率。它们是固定、已知语法的小样本，不是泛化准确率、随机benchmark或统计显著改善。

实际触发的修订仅1次，错误是JSON格式：原模型在第二个动作对象前多输出了引号。程序没有删引号代填，而是保留原始文本与错误反馈，让同一模型实例重新输出完整提案。修订轮工作器耗时3.115秒；加载阶段日志确认两轮合计只加载1次模型。不能将它解读成消除了首次冷启动、所有请求都能在数秒返回，或无需资源预算。

遗漏动作、时间不匹配、保护轨破坏等修订分支有CPU边界检查，但本组真实请求未触发，**尚未证明这些语义错误的实机修复收益**。已有视觉判断仍未校准，自动视觉修订保持关闭。

所有编排请求均确认没有自动创建视频任务。用于端到端验证的新视频由操作脚本在检查通过后另行显式提交，不能把它写成模型自主执行。原始请求、两轮提案、阶段耗时与运行结果保留在工作区`reports/interactworld-creator-plan-repair-20260926/`，媒体只留服务器数据盘。
