# 精确时间线编辑与历史版本分支

Creator 在原有模型编排和人工审核流程上增加两项能力：指定历史计划作为编辑基线；将明确秒数编译为受保护的逐帧控制修改。仍使用原视频模型，不是新训练或画质优化。

## 页面操作

1. 选择会话，在“编辑基线”中选择一个可执行版本，或在历史卡点击“基于此版修改”。默认动态跟随最新可执行计划，但提交时会绑定页面实际展示的版本。
2. 输入“保持前进不变，只在第8到10秒抬头，其他不要动”。编排不会自动生成视频。
3. 核对实际基线、修改摘要、完整时间线，再提交生成。选择对比对象和接受版本不会偷偷改变编辑基线。

基线是版本选择器中的真实 ID，不从文本“版本 A”猜测。可以从尚未生成视频的合法草稿分支；不能从无效计划或另一会话分支。旧客户端省略 `base_version_id` 时继续采用最新可执行计划。请求重放绑定原始基线，不因之后出现新版本而变更。

## 模型提议，程序编译

精确时间请求使用小的类型化 Patch，而非让模型重写全部240帧：

```json
{
  "status": "ready",
  "explanation": "将抬头控制限定在第8到10秒。",
  "edit_scope": "camera",
  "goals": ["镜头在指定区间向上俯仰"],
  "edits": [{
    "op": "replace_intervals",
    "key": "I",
    "intervals": [{"start_seconds": 8, "end_seconds": 10}]
  }]
}
```

`replace_intervals` 替换指定键的整条时间轨：此例仅在 `[8,10)` 秒激活 I，清除它原有的其他激活区间；其余7个键逐帧照抄基线。它并不承诺重新生成视频的其余像素不变。

16 FPS下上述区间为0基第128–159帧，共32个控制帧。秒数采用精确十进制换算，拒绝不落在1/16秒边界的值，不四舍五入；同时检查0–15秒范围、正时长、同键重复编辑、重叠区间、相反方向按键、保护范围。输出包含完整 `action_segments` 与重新计算的 `edit_patch`，不信任模型自报“已保留”。

下游从用户原话独立解析受支持的时间约束，核对模型提案的目标键和区间。旧完整时间线提案仍兼容，但“先后”“全程”“前后半段”不能只检查方向集合。例如要求先前进后抬头，反排的 I→W 提案会被拒绝。

精确编辑的控制摘要从最终编译轨道重建，包括未修改轨道，不直接沿用模型可能错误的时间描述。结构错误或非法JSON明确要求澄清，原提案或原始文本另存；不会修补JSON、静默切换规则，或把错误提案标为可执行。模型产生合法结构与正确意图仍需分别验证。

## 程序支持范围（不代表模型稳定理解率）

- `保持前进不变，只在第8到10秒抬头，其他不要动`
- `全程前进，8-10秒抬头`
- `前5秒前进，然后抬头3秒`：W `[0,5)`、I `[5,8)`，其余时间空输入。
- `第1.25到4.5秒前进`：精确支持可对齐帧边界的小数。
- 旧版缩短、延长、取消和半段指令继续兼容。

这仍是有限的中文时间语法，不是任意语言理解。未识别修饰词、语义冲突、非整帧时间和精确导航应澄清或拒绝，不丢词凑出可执行计划。“到桥边”不是“按W几秒”的同义词。

## API 与复现

`POST /api/plan` 可添加 `base_version_id`，并必须同时提供 `session_id`。响应 `planned_version_id` 标明本次实际创建或幂等复用的计划，不应把 `versions[-1]` 无条件当作本次结果。版本保存实际 `base_version_id` 和 `parent_version`。

通过现有部署的真实API提交一次指定基线生成（会消耗已授权GPU预算）：

```bash
python scripts/creator_delivery.py --url http://127.0.0.1:8881 \
  --case edit --session-id SESSION --base-version-id VERSION \
  --text '保持前进不变，只在第8到10秒抬头，其他不要动' \
  --max-seconds 2400 --output /DATA_DISK/new-temporal-result.json
```

## 验证边界

CPU检查区分意图、模型提案、编译结果与保护轨；浏览器测试使用明确的API替身，不是真实生成证据。真实模型/视频结果另行记录，不把软件测试数当成理解准确率或视频成功率。自动视觉修订仍默认关闭，最终画面评价与版本接受保留人工操作。
